# Full-Stack Assignment
## LLM Chatbot with Key Failover and Response Caching

**Time limit:** 24 hours from when you receive this assignment.

**Submission:** Live frontend and backend URLs, a public GitHub repository, and a 2–3 minute demo video. Submission Form.

**Tech stack:** React for the frontend, Python (with FastAPI) backend, and SQLite for storage.

**Tooling:** Any AI tools, code assistants, or documentation are allowed. The assignment emphasizes execution, resilience, architecture, and deployment.

---

## 1. Objective

This assignment tests whether you can build and ship a small, real-world AI application from end to end.

The project should demonstrate the ability to:

- Build a working full-stack app and deploy it live.
- Integrate an AI model and keep conversation context.
- Handle failures gracefully so the app keeps working when an API key fails.
- Improve speed and cost with caching.
- Think through problems and explain design decisions.

## 2. System Requirements

### Frontend (UI)

- A clean web interface to send messages and view a multi-turn conversation.
- Next to each AI reply, show that request's metadata:
  - Resolution source: `LLM_CACHE` or `LIVE_INFERENCE`
  - Model used: name of the model that answered
  - Latency: response time in milliseconds
  - Token usage: input and output tokens for that request only, never a conversation total
- Optional: a field to set a system prompt for the session.

### Backend and LiteLLM Gateway

- **Multi-turn state:** The backend stores history per session so the bot remembers earlier messages in the active chat.
- **Key pool and auto-fallback:** Configure LiteLLM with at least 2 API keys across one or more models. When a key returns HTTP 429, a quota error, or a 5xx, fail over to the next key automatically. The user must never see a broken screen or an unhandled exception.
- **Response caching:** Enable LiteLLM's built-in cache (in-memory or disk) and report `LLM_CACHE` when a cached response is used and `LIVE_INFERENCE` when a new one is generated.
- **Per-request token tracking:** Return input and output tokens with every response.

### Storage (SQLite)

- SQLite only: session history is stored in SQLite. No external services such as Redis or Postgres.
- Database file lives under a Docker volume, for example `/data/app.db`, set through `DATABASE_URL`, so history survives container restarts.
- Schema must be created automatically on startup.

Minimal data model:

```sql
CREATE TABLE messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    role       TEXT NOT NULL,   -- 'user' or 'assistant'
    content    TEXT NOT NULL,
    metadata   TEXT,            -- JSON string, assistant messages only
    created_at TEXT NOT NULL    -- server time, ISO-8601
);
```

Additional columns, indexes, or tables may be added.

### Deployment (Mandatory)

- Frontend must be deployed and public, e.g. Vercel, Netlify, Render, or Cloudflare Pages.
- Backend must be deployed and running, e.g. Render, Railway, Fly.io, or Hugging Face Spaces.
- Both tiers must be connected and testable through live URLs.

**Important:** The backend and frontend must follow the exact API and UI contract in Sections 3–5. A renamed field or a different path counts as a missing requirement.

## 3. Backend API Contract

The backend exposes exactly these three endpoints under its base URL. All bodies are JSON. Extra response fields are allowed; missing or renamed fields are not.

### GET `/health`

Returns HTTP 200 once the app is running, the database is reachable, and the key pool is loaded.

```json
{
  "status": "ok",
  "keys_configured": 2,
  "cache_enabled": true
}
```

### POST `/chat`

Request:

```json
{
  "session_id": "s-7f3a",
  "message": "What is the capital of France?"
}
```

Fields:

| Field | Type | Rule |
|---|---|---|
| `session_id` | string | Required, 1–128 chars, generated by the client. An unknown id starts a new session. |
| `message` | string | Required, 1–4000 chars after trimming whitespace. |
| `system_prompt` | string | Optional; overrides the default system prompt for this session. |

Response 200:

```json
{
  "session_id": "s-7f3a",
  "reply": "The capital of France is Paris.",
  "metadata": {
    "resolution_source": "LIVE_INFERENCE",
    "model": "gemini/gemini-2.0-flash",
    "latency_ms": 812,
    "input_tokens": 42,
    "output_tokens": 9,
    "key_id": "key_1",
    "fallback_attempts": 0
  }
}
```

Response field meanings:

| Field | Type | Meaning |
|---|---|---|
| `session_id` | string | Echo of request value |
| `reply` | string | Assistant text, non-empty |
| `resolution_source` | string | Exactly `LIVE_INFERENCE` or `LLM_CACHE` |
| `model` | string | LiteLLM model name that produced the reply |
| `latency_ms` | integer | Server-measured request time in milliseconds |
| `input_tokens` | integer | Prompt tokens for this request: system + history + new message |
| `output_tokens` | integer | Completion tokens for this reply |
| `key_id` | string or null | ID of key that answered (`key_1`, `key_2`, ...); null on `LLM_CACHE`; never expose the key itself |
| `fallback_attempts` | integer | Keys that failed before success; 0 on `LLM_CACHE` |

### GET `/sessions/{session_id}/messages`

Returns stored history for one session from SQLite, oldest first, without the system prompt.

Example:

```json
{
  "session_id": "s-7f3a",
  "messages": [
    {
      "role": "user",
      "content": "What is the capital of France?"
    },
    {
      "role": "assistant",
      "content": "The capital of France is Paris.",
      "metadata": {
        "resolution_source": "LIVE_INFERENCE",
        "input_tokens": 42,
        "output_tokens": 9
      }
    }
  ]
}
```

### Errors

Every error must be JSON with a `detail` field. Never return a stack trace or HTML error page.

A request that fails with 422 or 503 must not be added to session history.

| Case | Status | Body |
|---|---:|---|
| Missing/empty message or session_id, message over 4000 chars, malformed JSON | 422 | `{"detail": ...}`; FastAPI default shape is acceptable |
| Every key failed due to rate limit, quota, or 5xx | 503 | `{"detail": "all providers unavailable"}` |
| Unknown session in GET `/sessions/...` | 404 | `{"detail": "session not found"}` |

### Behavior Rules

- **Cache key:** model + full message list sent to the LLM (system prompt + history + new message).
- The same first message sent in a new session must return `LLM_CACHE` the second time.
- A different message must never come from cache.
- **Cache hit:** returns identical reply text. Tokens are the usage stored with the cached response; `key_id` is null.
- **Multi-turn:** history is stored in SQLite per `session_id`. The client sends only the new message.
- **Tokens:** per request, never a running total. Two equal-length first messages in two new sessions should report about the same `input_tokens`.
- **Latency:** `latency_ms` is an integer in milliseconds. A cache hit must be faster than a live call.

## 4. Failover Test Hook

`POST /chat` must support an `X-Simulate-Failure` request header. It makes chosen keys fail inside that one request only, allowing failover to be demonstrated without exhausting real keys.

Examples:

```text
X-Simulate-Failure: key_1=429
X-Simulate-Failure: key_1=429,key_2=500
X-Simulate-Failure: *=429
```

Rules:

- Format: comma-separated `<key_id>=<status>` pairs.
- `*` means every key.
- Supported statuses: `429`, `500`, `502`, `503`.
- Each listed key behaves as if its provider returned that status for this request only.
- The header is honored only when `ENABLE_FAILURE_SIMULATION=true`.
- This setting must be enabled on the deployed backend.

With two configured keys:

| Header | Expected response |
|---|---|
| `key_1=429` | 200, `key_id = key_2` |
| `key_1=500` | 200, `key_id = key_2` |
| `*=429` | 503 `{"detail":"all providers unavailable"}`, and nothing added to history |

A simulated request that succeeds through fallback must return a real answer, never an error message wrapped in HTTP 200.

## 5. Frontend Contract

Add the following `data-testid` attributes to the UI. Styling and layout are up to the implementation.

| `data-testid` | Element | Content |
|---|---|---|
| `chat-input` | Text input or textarea for user message | Empty after sending |
| `send-button` | Button that sends message | Enter may also send |
| `assistant-message` | Container of each assistant reply | Reply text plus metadata elements |
| `meta-source` | Inside each `assistant-message` | Exactly `LIVE_INFERENCE` or `LLM_CACHE` |
| `meta-model` | Inside each `assistant-message` | Model value |
| `meta-latency` | Inside each `assistant-message` | Latency, e.g. `812 ms` |
| `meta-input-tokens` | Inside each `assistant-message` | `input_tokens` integer |
| `meta-output-tokens` | Inside each `assistant-message` | `output_tokens` integer |
| `system-prompt-input` | Optional system-prompt field | Only if this optional feature is built |

Additional frontend behavior:

- A new session starts on each page load.
- Errors such as 422 and 503 show as readable messages in the chat, never a blank screen.
- The deployed frontend talks to the deployed backend.
- The backend allows the frontend origin.

## 6. Docker (Mandatory)

The whole stack must start locally with:

```bash
make up
```

Expected local URLs:

- Backend: `http://localhost:8000`
- Frontend: `http://localhost:3000`

Requirements:

- Multi-stage Dockerfiles for backend and frontend, using small runtime images.
- Root `docker-compose.yml` runs both services.
- A named volume is mounted at `/data` for the SQLite file.
- Root `Makefile` contains `up` and `down`.
- All configuration is through environment variables.
